# 3. Loading and Usage

With our `@Config` definitions built, MittenLib has generated the implementation, validation, and loading logic. 
The final step is to integrate this into your application.

MittenLib is designed from the ground up to work seamlessly with **Guice**, which is the recommended way to load and access your configurations.

## Integrating with Guice

To load a configuration automatically, your DTO must declare a **`@Source`**:

```java
@Config
@Source("config.yml") // Tells MittenLib this config maps to a specific file
public interface AdvancedConfig {
    // ...
}
```

When `@Source` is present, the processor generates a `CONFIG` constant on the implementation class. You use this constant to install the `ConfigModule`.

### What happens here?
1. `MittenLib.withDefaults(this)` sets up the default loaders (YAML, JSON), formatters, and path resolvers relative to your plugin's data folder.
2. `addConfigModule(new ConfigLoaderModule())` registers the module generated by the annotation processor. This single module automatically binds all your `@Config` implementations, deserializers, and validators into the Guice context.
3. When the `Injector` is created, MittenLib reads `config.yml`, parses it, validates it against your constraints, and binds the resulting `AdvancedConfig` instance to the Guice container.

## Using the Configuration

Once bound, you can inject your configuration anywhere in your application using `ConfigProvider<T>`.

### Why `ConfigProvider<T>`?
You inject a `ConfigProvider` instead of the raw `AdvancedConfig` instance. This allows for **dynamic reloading**. 
If you implement a command to reload your plugin's configuration, the `ConfigProvider` will always yield the freshest, newly-validated instance of the config when `get()` is called, without needing to recreate your dependent classes.
