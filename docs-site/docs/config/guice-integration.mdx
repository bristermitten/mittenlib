# Guice Integration

MittenLib's Guice integration transforms configuration from a manual chore into an automatic, dependency-injected service. Define your DTO, annotate it with `@Source`, and MittenLib handles loading, caching, and even hot-reloading.

## Automatic Loading with `@Source`

Link a DTO to a specific file using the `@Source` annotation:

```java
import me.bristermitten.mittenlib.config.*;

@Config
@Source("config.yml")
public class PluginConfigDTO {
    String pluginName = "MyPlugin";
    int version = 1;
}
```

### Registering with Guice

In your plugin's Guice module, install the `ConfigModule`:

```java
public class MyPluginModule extends AbstractModule {
    @Override
    protected void configure() {
        install(new ConfigModule(PluginConfig.CONFIG));
    }
}
```

The `PluginConfig.CONFIG` constant is generated by the annotation processor and contains all the metadata needed to load and manage the config.

### Injecting Configs

Once registered, inject your config anywhere:

```java
public class MyService {
    private final PluginConfig config;
    
    @Inject
    public MyService(PluginConfig config) {
        this.config = config;
    }
    
    public void doSomething() {
        System.out.println("Plugin: " + config.pluginName());
    }
}
```

## Provider-Based Injection

For advanced features like lazy loading and reloading, inject a `Provider<PluginConfig>` or `ConfigProvider<PluginConfig>`:

```java
public class MyService {
    private final Provider<PluginConfig> configProvider;
    
    @Inject
    public MyService(Provider<PluginConfig> configProvider) {
        this.configProvider = configProvider;
    }
    
    public void doSomething() {
        // Config is loaded on first access (lazy loading)
        PluginConfig config = configProvider.get();
        System.out.println("Plugin: " + config.pluginName());
    }
}
```

### Why Use Providers?

| Feature | Direct Injection | Provider Injection |
|---------|-----------------|-------------------|
| Lazy Loading | No | Yes |
| Hot Reloading | No | Yes |
| File Path Access | No | Yes (with ConfigProvider) |

## ConfigProvider Features

The `ConfigProvider<T>` interface extends `Provider<T>` with additional capabilities:

```java
public class MyService {
    private final ConfigProvider<PluginConfig> configProvider;
    
    @Inject
    public MyService(ConfigProvider<PluginConfig> configProvider) {
        this.configProvider = configProvider;
    }
    
    public void printInfo() {
        PluginConfig config = configProvider.get();
        
        // Access the file path
        Path configPath = configProvider.path();
        System.out.println("Loaded from: " + configPath);
        
        // Force a reload
        configProvider.clearCache();
        PluginConfig freshConfig = configProvider.get();
    }
}
```

## File Watching & Hot Reloading

Enable automatic config reloading when the file changes on disk:

```java
public class MyPluginModule extends AbstractModule {
    @Override
    protected void configure() {
        install(new ConfigModule(PluginConfig.CONFIG));
        install(new FileWatcherModule()); // Enables hot reloading
    }
}
```

With `FileWatcherModule` installed:
- Configs are automatically reloaded when the file is modified
- No restart required
- Provider-based injection ensures your service always gets the latest config

## Initialization Strategies

Control how config files are initialized when they don't exist:

### Default Strategy

By default, if the config file doesn't exist, loading will fail. You can provide a default config using the initialization strategy:

```java
@Config
@Source(value = "config.yml", strategy = ConfigInitializationStrategy.CREATE_WITH_DEFAULTS)
public class PluginConfigDTO {
    String pluginName = "MyPlugin";
    int maxPlayers = 20;
}
```

This will create the config file with the default values if it doesn't exist.

### Custom Path Resolution

For plugins, configs are typically resolved relative to the plugin's data folder:

```java
@Config
@Source(value = "config.yml", resolver = PluginConfigPathResolver.class)
public class PluginConfigDTO {
    // ...
}
```

The `PluginConfigPathResolver` automatically resolves paths relative to your plugin's data directory.

## Multiple Configs

Register multiple configs in a single module:

```java
public class MyPluginModule extends AbstractModule {
    @Override
    protected void configure() {
        install(new ConfigModule(PluginConfig.CONFIG));
        install(new ConfigModule(DatabaseConfig.CONFIG));
        install(new ConfigModule(MessagesConfig.CONFIG));
    }
}
```

Each config is loaded independently and can be injected separately.

## Error Handling

Config loading errors during Guice initialization will throw `ConfigLoadingErrors`, which contains all failures. This ensures your plugin fails fast with clear error messages.

```java
try {
    Injector injector = Guice.createInjector(new MyPluginModule());
} catch (ConfigLoadingErrors e) {
    getLogger().severe("Failed to load configs:");
    e.getErrors().forEach(error -> 
        getLogger().severe("  - " + error.getMessage())
    );
}
```
